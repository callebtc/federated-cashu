# 36.02 · Output key construction: rules and edge cases

Variation 2 of slide 36 (Three tags, one output key) · lens: Advanced · deck `fcv-g-json-taproot` page 20 · 6 steps · script 140 words, about 60 s

## Script

**[1]** Keys are 32-byte x-coordinates; lift_x takes the point with even y. A secret whose point has odd y is negated before the tweak. Using only x keeps each signature valid for exactly one key.

**[2]** The tweak is TapTweak of p and the root, as an integer. If it is at least n, the group order, construction fails, with probability below 2 to the minus 127. Script path spends reveal the parity of y(Q).

**[3]** Without scripts, commit to an empty tree anyway. Otherwise a party in a non-MuSig key aggregate can hide a script path in its key.

**[4]** To disable the key path, use H + r·G with fresh r; a bare H would show there is no key path.

**[5]** Leaf versions are even, never 0x50. Branches sort their children. Depth is at most 128.

**[6]** BIP341's Python reference and test vectors.

## Background

- **lift_x**: takes a 32-byte x and returns the curve point with that x and even y, or fails if x is not on the curve.
- **Negating a secret**: the points d·G and (n − d)·G share x and have opposite y parity. If d·G has odd y, n − d is the secret of the even-y point that the x-only key stands for.
- **One key per signature (BIP340)**: if a verifier accepted both points with a given x, every signature would be valid for two public keys; BIP340 avoids this by treating x alone as the key.
- **Group order n**: the number of points generated by G, slightly below 2^256. 2^256 − n is about 2^128.3, so a hash output at or above n occurs with negligible probability.
- **Empty-tree commitment**: Q = P + hash_TapTweak(p)·G. BIP341's attack: when the aggregate key is a plain sum of the parties' keys, one party can add t·G to its own key so that the sum commits to a script path only it knows. MuSig randomizes the aggregate key, so the attack does not apply to MuSig.
- **NUMS point H**: "nothing up my sleeve": `lift_x(50929b74…ce803ac0)`, the x-coordinate being SHA-256 of the uncompressed encoding of G. Nobody knows its discrete logarithm. Revealing r proves to a chosen verifier that the key path is disabled.
- **Leaf version constraints**: the low bit of control byte 0 holds the parity, so versions are even; 0x50 would be ambiguous with the annex. 0xc0 is BIP342 tapscript.
- **Compact size**: scripts of 253 bytes or more use a 3-byte length prefix: 0xfd, then 2 bytes little-endian.
- **Reference code**: `taproot_tweak_pubkey`, `taproot_tweak_seckey`, `taproot_tree_helper` in BIP341; vectors in `bip-0341/wallet-test-vectors.json`.
